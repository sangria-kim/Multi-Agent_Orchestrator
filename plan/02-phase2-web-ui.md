## 1. API

서버가 하는 일은 **작업 폴더를 읽어 JSON으로 돌려주는 것**과 **실행을 시작하는 것** 둘뿐이다.

| Method | 경로 | 설명 |
|---|---|---|
| POST | `/api/tasks` | 작업 폴더 생성 + 즉시 실행. `{ taskId }` 반환 |
| GET | `/api/tasks` | 작업 목록. 폴더 이름 역순 |
| GET | `/api/tasks/{taskId}` | Task 하나. 메타데이터 + Agent별 상태 + 결과 본문 |
| POST | `/api/tasks/{taskId}/agents/{agent}/retry` | 해당 Agent만 재실행 |
| GET | `/api/agents` | 사용 가능한 Agent 목록과 설치 여부 |

전부 파일을 읽어 만든다. 캐시하지 않는다. 로컬 디스크에서 JSON 두 개와 마크다운 두 개를 읽는 비용은 무시할 수 있고, 캐시를 두면 파일이 진실이라는 전제(원칙 5)가 깨진다.

`GET /api/tasks/{taskId}`는 **결과 본문까지 함께 담아 돌려준다.** 결과가 파일 두 개뿐이라 별도 엔드포인트로 나눌 이유가 없다. 화면이 필요한 걸 요청 한 번으로 받는다.

`GET /api/agents`는 각 Adapter가 `<cli> --version`을 돌린 결과를 모은다. **이건 프로세스 수명 동안 캐시해도 된다.** 파일이 아니라 환경을 조회하는 것이라 원칙 5와 충돌하지 않는다. **확인 범위는 "설치되어 있고 실행 가능한가"까지다.** 인증 유효성은 보지 않는다. 확인하려면 실제 요청을 보내야 해서 화면 진입마다 비용과 지연이 붙는다. 인증 만료는 실행 실패의 `error.txt`로 드러나며, 그 문구를 그대로 보여주는 것으로 충분하다.

### 상태 갱신은 폴링으로 한다

실행 중일 때만 `GET /api/tasks/{taskId}`를 **1초 간격으로** 다시 부른다. Task 상태가 종료 상태가 되면 폴링을 멈춘다.

SSE를 쓰지 않는 이유는 원칙 5다. 진실은 파일에 있고 서버는 파일을 읽어 돌려줄 뿐이므로, 서버가 클라이언트에게 밀어 보낼 상태를 따로 들고 있을 이유가 없다. 스트리밍을 하려면 실행 중 출력을 메모리에 버퍼링하고 구독자를 관리하고 연결 해제를 감지해야 하는데, 그 전체가 "1초마다 파일 두 개 읽기"로 대체된다. 새로고침 복원도 공짜로 따라온다.

대가는 진행 중인 부분 출력을 볼 수 없다는 것이다. 완료될 때까지 `Running`과 경과 시간만 보인다. 대표 사용 사례 셋이 모두 문서 한 편을 통째로 받는 작업이라 부분 출력의 가치가 낮다고 보고 받아들였다.

## 2. 화면

### 2.1 요청 입력 (`/`)

| 항목 | 형태 |
|---|---|
| 요청 제목 | 한 줄 입력. **선택 항목.** 작업 폴더 이름과 목록 식별에 쓰인다. 비우면 목록에 요청 내용 앞부분이 제목 자리에 표시된다 |
| 요청 내용 | 여러 줄 입력. 필수 |
| 추가 Context | 여러 줄 입력. 선택 |
| 실행 Agent 선택 | Claude / Codex 체크박스. 기본 전부 선택 |
| 실행 버튼 | 요청 내용이 있고 Agent가 1개 이상 선택되면 활성화 |

**제목은 실행 버튼 활성화 조건에 넣지 않는다.** Runner 검증도 제목을 요구하지 않는다. 두 곳이 어긋나면 버튼은 눌리는데 서버가 400을 던진다.

체크박스 목록은 `GET /api/agents` 결과로 생성한다. 하드코딩하지 않는다. 설치되지 않은 Agent는 비활성화하고 사유를 옆에 표시한다.

제출하면 `/tasks/{taskId}`로 이동한다.

**요청 내용 입력란 아래에 대표 사용 사례 세 개를 예시 버튼으로 둔다.** 누르면 해당 예시 문구가 입력란에 채워진다.

| 버튼 | 채워지는 예시 |
|---|---|
| 계획서 작성 | 신규 기능 구현 계획서를 작성해줘. PM과 개발자가 구현 전에 범위와 구현 순서를 합의할 수 있는 문서여야 한다. |
| 조사 / 아이디어 | 사용자 인증 방식을 무엇으로 할지 조사해줘. 후보를 3개 이상 제시하고 각각의 장단점과 우리 상황에서의 적용 조건을 정리해줘. |
| 문서 포맷 제안 | PRD의 Markdown 포맷을 제안해줘. 각 Section의 목적을 함께 설명해줘. |

빈 화면 앞에서 뭘 적을지 막히는 걸 줄인다. 이 도구는 요청 문구의 질이 결과의 질을 그대로 결정한다.

### 2.2 실행 상태 (`/tasks/{taskId}` 상단)

Agent별 한 행씩 표시한다.

| Agent | Status | 실행 시간 | Action |
|---|---|---|---|
| Claude | Completed | 42s | 재실행 |
| Codex | Running | 31s | — |

Agent 상태는 `Queued` `Running` `Completed` `Failed` `Timeout` 다섯 가지다. 각각 색으로 구분한다. `Queued`는 구간이 매우 짧아 실제로는 보이지 않을 수 있다.

**Task 상태는 Agent 상태와 별개다.** 두 개를 섞지 않는다.

| Task 상태 | 의미 | 종료 상태인가 |
|---|---|---|
| `running` | 하나라도 실행 중 | 아니오 |
| `completed` | 전부 성공 | 예 |
| `partial_completed` | 일부만 성공 | 예 |
| `failed` | 하나도 성공 못 함 | 예 |

**종료 상태 집합 = `completed` | `partial_completed` | `failed`.** 폴링 중단 조건과 작업 목록 배지가 모두 이 집합을 쓴다. `partial_completed`를 빠뜨리면 한쪽만 성공한 Task가 **영원히 1초 폴링**하고, 과거 Task를 열 때마다 폴링이 하나씩 붙는다. 폴링 중단 규칙이 막으려던 바로 그 증상이다.

실행 시간은 `Running` 중에는 `startedAt` 기준으로 클라이언트에서 1초마다 증가시키고, 종료 후에는 `executionTimeMs`로 고정한다. 진행 중에도 시간이 흐르는 게 보여야 멈춘 것처럼 느껴지지 않는다.

재실행 버튼은 종료 상태에서만 활성화한다. 실행 중에는 누를 수 없다.

작업 폴더 경로를 헤더에 그대로 표시한다. 복사 버튼을 함께 둔다. 원칙 5를 화면에서도 지키는 셈이고, 실제로 에디터로 열고 싶은 순간이 자주 온다.

### 2.3 diff view (`/tasks/{taskId}` 본문)

**이 화면이 Phase 2의 핵심이다.** 두 결과를 나란히 놓는 2단 레이아웃이고, 두 가지 보기 모드를 탭으로 전환한다.

| 모드 | 내용 | 기본값 |
|---|---|---|
| **나란히 보기** | 양쪽 마크다운을 렌더링해 2단으로. 스크롤 동기화 (단순 비율) | ✓ |
| **섹션 비교** | 양쪽의 마크다운 헤딩만 뽑아 표로 나열 | |

#### Agent를 하나만 선택했을 때

**diff view 대신 단일 결과 뷰로 폴백한다.** 모드 탭을 숨기고 결과 하나를 전체 폭으로 보여준다. 비교 대상이 없는데 2단 레이아웃을 그리면 빈 열이 남는다.

Agent 선택은 1개도 허용되므로(검수 2번) 반드시 생기는 경로다.

#### 최신 attempt가 실패인데 이전에 성공한 적이 있으면

결과 영역에 **"이전 성공 결과 보기"** 한 줄을 둔다. 누르면 그 attempt의 `result.md`를 보여준다.

재실행 버튼이 `Completed`에서도 눌리기 때문에 생기는 경로다. 성공한 결과를 다시 돌렸다가 실패하면 멀쩡한 이전 결과가 화면에서 사라진다. `status.json`에 attempt 이력이 있으므로 **가장 최근의 `completed` attempt**를 찾는 건 추가 저장 없이 된다. 전체 attempt 목록 조회는 만들지 않는다.

#### 줄 단위 diff는 넣지 않는다

한때 세 번째 모드로 검토했으나 뺐다. 기록으로 남긴다.

두 Agent는 같은 요청을 받았을 뿐 **각자 처음부터 쓴 서로 다른 문서**다. 코드 diff처럼 공통 조상이 없다. 줄 단위로 비교하면 거의 모든 줄이 "양쪽 다 변경"으로 잡혀서 화면이 온통 빨강과 초록이 되고, 정작 알고 싶은 "둘이 무엇을 다르게 봤는가"는 묻힌다. 기본값으로 둘 수 없는 모드를 위해 diff 라이브러리와 렌더링 경로를 하나 더 들이는 건 값이 맞지 않는다.

두 결과를 동시에 보는 목적은 **나란히 보기**가, 구조 차이를 짚는 목적은 **섹션 비교**가 담당한다.

#### 섹션 비교

대표 사용 사례 셋 모두 "어떤 섹션으로 구성했는가"가 핵심 차이다. 마크다운 헤딩만 뽑아 표로 나열한다.

| 섹션 | Claude | Codex |
|---|---|---|
| Overview | ✓ | — |
| Objective | — | ✓ |
| Implementation Steps | ✓ | ✓ |
| Test Plan | — | ✓ |

같은 이름의 헤딩은 같은 행에, 한쪽에만 있는 헤딩은 반대쪽을 `—`로 둔다. 이름이 달라도 의미가 같은 섹션(`Overview` / `Objective`)은 **묶지 않는다.** 묶으려면 의미를 판정해야 하고, 그건 원칙 3(No Judgment by Tool)에 어긋난다. 순수 문자열 비교만 한다.

구현은 `remark`로 파싱할 것도 없이 `^#{1,6}\s` 정규식으로 충분하다. 코드 블록 안의 `#`만 제외하면 된다.

#### 공통 동작

- 스크롤 동기화는 **단순 비율**로 한다. 한쪽의 스크롤 위치 비율을 그대로 반대쪽에 적용한다. 길이가 크게 다른 두 문서에서는 대응이 어긋나지만, 헤딩을 짝지어 동기화하려면 섹션 매칭이 필요하고 그건 섹션 비교 모드가 할 일이다
- 마크다운은 `react-markdown` + `remark-gfm`으로 렌더링한다. **원문 보기 토글**을 함께 둬서 렌더링이 깨져도 원본을 확인할 수 있게 한다
- 각 열 상단에 Agent 이름, 상태 배지, **Markdown 복사** 버튼을 둔다
- 한쪽만 완료됐으면 그쪽부터 보여준다. 나머지는 "실행 중" 자리 표시자를 둔다. 둘 다 끝날 때까지 기다리지 않는다
- 실패한 쪽은 결과 대신 에러 사유와 재실행 버튼을 보여준다. `error.txt` 전문은 접은 상태로 두고 펼칠 수 있게 한다. CLI stderr는 길고 대부분 노이즈다

#### Agent가 셋이 되면

diff view는 V1에서 **유일하게 Agent 수 2를 전제한 부분이다.** 의도한 예외다. 2단 레이아웃과 섹션 비교표 모두 3열로 넓히면 좁은 화면에서 읽을 수 없다.

Gemini를 추가할 때는 diff view 위에 "비교할 두 Agent" 선택기를 얹는다. 실행과 저장은 3개를 그대로 처리하고, 보기만 두 개씩 고른다. 나머지 경로는 [01-phase1-execution.md](01-phase1-execution.md)의 규칙대로 Agent 수에 의존하지 않으므로 이 선택기 하나가 추가 작업의 전부다.

### 2.4 작업 목록 (`/tasks`)

작업 폴더를 이름 역순으로 나열한다. 검색도 필터도 페이지네이션도 없다.

| 열 | 내용 |
|---|---|
| 제목 | 클릭하면 `/tasks/{taskId}`로 이동 |
| 상태 | Task 상태 배지 |
| Agent 요약 | 두 Agent의 상태를 점 두 개로 압축 표시 |
| 생성 시각 | 상대 시간 (`3시간 전`), 툴팁에 절대 시각 |

목록에서 알고 싶은 건 "이 Task가 쓸 만한 결과를 냈는가"이지 개별 실행 시간이 아니다. 색만으로 Completed / Failed가 구분되면 충분하다.

한 번에 최근 50건만 읽는다. 더 필요하면 작업 폴더를 직접 열면 된다. 로컬 단일 사용자 도구에서 51번째 이전 작업을 웹에서 찾아야 하는 상황은 오지 않는다고 본다.

빈 목록일 때는 안내 문구와 함께 `/`로 가는 링크를 보여준다.

### 2.5 페이지 구성

| 경로 | 역할 |
|---|---|
| `/` | 요청 입력 |
| `/tasks/{taskId}` | 실행 상태 + diff view |
| `/tasks` | 작업 목록 |

상단 네비게이션에 "새 요청"(`/`)과 "작업 목록"(`/tasks`) 두 링크를 둔다.

폴링은 `useTask(taskId)` 훅 하나로 감싼다. Task 상태가 **종료 상태(`completed` / `partial_completed` / `failed`)**면 인터벌을 걸지 않는다. **과거 작업을 열 때마다 즉시 멈출 폴링이 하나씩 도는 걸 막는다.**

폴링이 `completed`인데 `result.md`가 아직 없는 응답을 받으면 **그 회차를 버리고 다음 회차를 기다린다.** 서버의 파일 쓰기 순서상 거의 생기지 않지만, 화면이 빈 결과를 확정 상태로 렌더링하는 것보다 한 박자 늦는 편이 낫다.

## 3. 검증

`AGENT_USE_MOCK=1`로 먼저 전체 흐름을 확인한 뒤 실제 CLI로 한 번 더 돌린다. Mock은 빠르고 결정적이라 UI 문제와 CLI 문제를 분리해서 볼 수 있다. 2026-09-21에 `pnpm dev:mock`(Mock 전체 흐름)과 `pnpm dev`(실제 CLI) 양쪽을 브라우저로 직접 조작해 아래 항목을 모두 확인했다.

- [x] `/`에서 제목·내용·Context를 입력하고 두 Agent를 선택해 실행할 수 있다
- [x] 예시 버튼 세 개가 각각 입력란을 채운다
- [x] 제출 즉시 `/tasks/{taskId}`로 이동하고 두 Agent가 모두 `Running`으로 보인다
- [x] 실행 시간이 1초마다 증가한다
- [x] 완료된 Agent의 결과가 먼저 나타난다. 나머지를 기다리지 않는다 — Mock에서 Claude/Codex 각자 다른 시점에 완료되는 것으로 확인
- [x] 두 결과의 내용이 서로 다르다 — 실제 CLI 결과로 확인(서로 다른 PRD 구조)

### 추가로 발견해 고친 문제

**`hookShutdown()`이 실제 서버 어디에서도 호출되지 않고 있었다.** Phase 1 스모크 스크립트에서만 호출했을 뿐, Next.js 앱 자체에는 연결돼 있지 않아 실제 `pnpm dev`를 Ctrl-C로 끄면 진행 중이던 `claude`/`codex` 자식 프로세스가 고아로 남는 것을 실제 프로세스 그룹에 `SIGINT`를 보내 재현했다. `src/instrumentation.ts`의 `register()`(Next.js가 서버 시작 시 한 번 호출하는 공식 훅)에서 `hookShutdown()`을 호출하도록 고쳤고, 같은 방식으로 재현해 자식 프로세스가 정리됨을 확인했다.
